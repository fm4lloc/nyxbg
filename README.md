# NyxBG

A wallpaper renderer for Wayland compositors implementing the `wlr-layer-shell` protocol.

NyxBG draws a static PNG or JPEG behind all other surfaces and then waits. It is not a compositor, desktop component, slideshow player, or animation engine. Once the wallpaper has been submitted to the compositor, the process remains blocked until the compositor or a signal wakes it.

*Leia em* [Português (Brasil)](README.pt-BR.md).

## Design

- ISO C11, POSIX.1-2008. No C++, GObject, or framework.
- Four required components: `wayland-client`, `libpng`, `libjpeg`, and the `wlr-layer-shell` protocol descriptions. No GTK, Qt, SDL, Cairo, OpenGL, or Vulkan.
- Software rendering through `wl_shm` buffers. No GPU context and no render loop.
- One responsibility per module; modules communicate through the interfaces in `include/`, never through globals.
- After the initial commit, the process blocks in a single `poll()` over two descriptors: the Wayland socket and a signal self-pipe.
- Every public function and public data type has a kernel-doc-style comment.

## Build

```sh
make
sudo make install            # installs to /usr/local
```

### Essential Requirements

| Requirement | Purpose |
|---|---|
| GCC 12+ or Clang 15+ | C11 compiler |
| `wayland-client` | Wayland client library |
| `wayland-scanner` | Protocol code generation |
| `libpng` | PNG decoding |
| `libjpeg-turbo` | JPEG decoding |
| `wlr-protocols` | `wlr-layer-shell` protocol description |
| `wayland-protocols` | Auxiliary Wayland protocol descriptions |

`wlr-protocols` is preferably obtained from the system. When unavailable, NyxBG can use a vendored copy from `protocol-xml/`.

### Targets and Options

```sh
make                         # release build, warnings are errors
make BUILD=debug             # -Og -g3, source-level debugging
make BUILD=asan              # AddressSanitizer + UndefinedBehaviorSanitizer
make BUILD=lto               # link-time optimization
make WERROR=0                # downgrade errors to warnings
make analyze                 # GCC static analyzer
make info                    # report what this build will actually use
make vendor                  # copy system XMLs to protocol-xml/
make PREFIX=/usr install
make clean
```

### Strict Build

The warning set is not advisory. Every diagnostic the compiler can emit for project-owned code is enabled, and `-Werror` remains active in all four profiles. A warning reaching the release build is a warning that should not be ignored.

Third-party headers are included through `-isystem`, not `-I`. Therefore, `libpng`, `libjpeg`, and `libwayland` do not have to satisfy the project's warning policy.

Protocol code generated by `wayland-scanner` is compiled separately and is not subjected to the same warning set as manually written code.

Compiler- and architecture-dependent flags are tested before use. `make info` reports exactly which options were accepted by the current toolchain.

`WERROR=0` exists as a compatibility mechanism for toolchains that produce new diagnostics. It is not the default behavior.

Hardening remains enabled in all profiles, including `_FORTIFY_SOURCE`, stack protector, stack-clash protection, PIE, full RELRO, non-executable stack, and control-flow protection when available on the target architecture.

`-fharden-compares` and `-fharden-conditional-branches` are deliberately not used because they add redundancy primarily intended for threat models involving physical faults or processor fault injection. `-fstack-protector-all` is also omitted because `-fstack-protector-strong` already covers the cases relevant to NyxBG.

### Protocol Code Source

`protocol/` contains generated code only. It is created by `make`, removed by `make clean`, and is not tracked by Git.

The XML used for generation is searched for in two locations, in this order:

1. **System**, through `pkg-config --variable=pkgdatadir` for `wlr-protocols` and `wayland-protocols`. This is the expected behavior for distribution packagers and allows updated protocol descriptions to reach NyxBG without vendored files.
2. **`protocol-xml/`**, vendored copies, when the system does not provide the files. `wlr-protocols` in particular is not packaged by every distribution: Arch and Alpine provide it; Debian does not. `make vendor` populates this directory from system copies.

`make info` reports which source won. If neither source contains a required file, the build stops with a message identifying the required package.

`xdg-shell.xml` is required for exactly one symbol: `zwlr_layer_surface_v1` has a `get_popup` request whose argument type is `xdg_popup`, so the generated interface table references `xdg_popup_interface`, even though NyxBG never creates a popup. Only its private code is generated; its client header is never included.

## Usage

```sh
nyxbg wallpaper.png
nyxbg --mode fit --color 101018 photo.jpg
```

| Option | Meaning |
|---|---|
| `-m`, `--mode MODE` | `fill` (default), `fit`, `stretch`, `center` |
| `-c`, `--color RRGGBB` | color drawn where the image does not reach (default `000000`) |
| `-v`, `--verbose` | diagnostic output on stderr |
| `-h`, `--help` | usage |
| `-V`, `--version` | version |

There is no configuration file or daemon. The image format is determined by magic bytes, not by the filename extension. See `man 1 nyxbg` for the complete description.

### Scaling Modes

| Mode | Behavior |
|---|---|
| `fill` | Covers the output. The excess axis is cropped and centered. |
| `fit` | Shows the entire image. Remaining area is filled with `--color`. |
| `stretch` | Covers the output while ignoring the source aspect ratio. |
| `center` | Preserves the original size and centers the image on the output. |

Downscaling uses a separable triangular filter whose support grows with the reduction factor, so every source pixel within the footprint contributes. A 1-pixel black/white checkerboard reduced by 5x converges to a uniform value instead of the moiré produced by bilinear or nearest sampling. This describes averaging the encoded sample values; NyxBG does not convert to linear light during this filtering step. Filtering is performed with premultiplied alpha, and the result is composited over `--color` before being written as opaque `XRGB8888`.

The two passes never construct a full intermediate plane. The vertical pass keeps a ring containing only the lines still required, over a column band narrow enough to keep the ring below a fixed 64 MiB limit. Thus, peak memory is a constant of the source rather than a function of image height or output width. A 2048x16384 source scaled to a 2560-pixel output keeps about 250 KiB of intermediate data; the same operation consumed 160 MiB before the ring existed.

### Signals

| Signal | Effect |
|---|---|
| `SIGHUP` | rereads the image from disk and redraws all outputs |
| `SIGINT`, `SIGTERM` | releases all Wayland resources and exits |

A failed reload is not fatal: the wallpaper already on screen remains.

## Runtime Behavior

- Each output receives its own layer surface on the background layer, anchored to all four sides, with exclusive zone `-1` so panels and docks do not reduce its area.
- The surface has an empty input region, so pointer and touch events pass through to whatever is underneath.
- The opaque region covers the entire surface, allowing the compositor to skip blending.
- Monitors may be connected and disconnected at any time. A new output receives the wallpaper; a removed output releases its surface and buffers.
- A resolution change arrives as a layer-surface configure and triggers a redraw. A scale change is obtained from `wl_output`.
- No `wl_surface.frame` callback is requested. NyxBG does not animate, therefore it does not participate in the frame clock.

## Security Model

NyxBG does not execute external programs, open network sockets, implement IPC, write configuration files, or modify the source image. It reads one local file and communicates with one Unix socket.

Two inputs are part of the program's operational model.

**The image file**, because a wallpaper may have been downloaded or shared. Dimensions are limited (32767 per axis, 134,217,728 pixels in total), and the limit is applied to the dimensions declared by the *header*, before a call that could allocate from them — `jpeg_start_decompress()` builds the complete coefficient set for a progressive image, so checking afterwards would be too late. Auxiliary chunks are also limited: the libpng specification allows hundreds of compressed text chunks in a small file to retain gigabytes, and an allocation failure may be reported as a warning; therefore NyxBG limits this to 32 chunks of 256 KiB. Embedded textual metadata, ICC profiles, and EXIF are not interpreted. This keeps decoding focused on pixel data. In particular, JPEG EXIF orientation is not applied; the image must be exported with the desired orientation already applied.

**The compositor** is a separate process that supplies protocol events to the client. Sizes received through `configure` and the scale factor received from `wl_output.scale` are bounded at input, before they participate in arithmetic. Buffer size is also checked against `INT32_MAX`, because the per-axis limit alone does not bound the product, and pixel count is limited to 2^27 — a 512 MiB buffer, still leaving room for an 8K panel at integer scale 2. The number of buffers a surface may retain simultaneously is also limited. Values outside these bounds produce diagnostics and rendering does not proceed.

## Known Limitations

- **Fractional scaling.** Buffers are rendered at the output's *integer* scale. Under a fractional scale such as 1.5, the compositor resamples our buffer at scale 2. This fallback remains outside NyxBG's native fractional-scaling path. Compositor-coordinated support requires `wp_viewporter` and `wp_fractional_scale_v1`, which are outside the scope of 1.0.
- **Image orientation.** JPEG EXIF orientation is not interpreted. Pixels are used as stored by the decoder.
- **Color management.** Embedded ICC profiles are not interpreted and NyxBG does not perform output-specific color management. The renderer operates on the RGB representation provided by the image decoder.
- **Linear-light filtering.** The resampling filter operates on RGB values from decoded samples rather than first converting them to linear light. This preserves the current rendering path and is generally difficult to notice in photographic content, although synthetic high-contrast patterns may show a larger difference. A linear-light path is not part of the 1.0 default.
- **No buffer sealing.** Shared-memory buffers are not sealed with `F_SEAL_SHRINK`; compositors must handle `SIGBUS` as appropriate for other `wl_shm` clients.
- **One image per output.** Different wallpapers per output are the responsibility of a wallpaper manager, which NyxBG deliberately is not.

## Structure

```text
nyxbg/
├── include/       one header per module
├── src/           one translation unit per module
├── protocol-xml/  vendored protocol descriptions, used when the system
│                  does not provide them
├── protocol/      generated by make, removed by make clean, not tracked
├── LICENSE
├── Makefile
├── nyxbg.1
├── README.md
└── README.pt-BR.md
```

| Module | Responsibility |
|---|---|
| `main.c` | entry point, CLI, event loop, shutdown |
| `wayland.c` | connection, registry, globals |
| `layer.c` | layer-surface creation, anchors, configure |
| `output.c` | output discovery, hotplug, resolution, scale |
| `image.c` | PNG and JPEG decoding to RGBA |
| `scale.c` | geometry only; no pixels are touched here |
| `render.c` | `wl_buffer` allocation, resampling, damage, attach, commit |
| `signal.c` | signal handling through the self-pipe |

`include/signal.h` deliberately shares its name with the system header. The Makefile adds `include/` with `-iquote`, so `"signal.h"` finds the project header while `<signal.h>` continues to find the libc header.
